# Bosun 0.28 — tenant isolation, metrics and defaults

Proposal against `v0.27.1` (`91444f7`). The 0.28 release adds an optional Linux bubblewrap sandbox with one worker per tenant and tenant-owned browser processes, profiles, downloads, recordings and allowed egress exits. By default, zero or one configured tenant token uses the 0.27 single-process deployment, and two or more tokens enable the tenant sandbox. Browser metrics work in both modes, and sandboxed workers also export cgroup metrics. Running multiple tenants in one process requires an explicit unsafe override. The release also introduces neutral deployment defaults and a shared configuration schema. Credential APIs and behavior stay as in 0.27, including `secret_create`, `secret_save`, `secret_reveal` and `secrets_reveal`. `?` marks an estimate or an unverified implementation assumption.

## 1. Threat model

| Actor | Trust and authority |
| --- | --- |
| Operator | Trusted to run the host, kernel, gateway and workers and to assign tenants. Host root can inspect memory and files. Use a worker on a host you trust. |
| Tenant agent | Its authenticated runtime can drive that tenant's browser under its token policy. |
| Model | Can request actions under the tenant's token policy and see ordinary browser results, which can contain prompt injection. It can act with any browser login the operator chooses to make available to it. |
| Web pages | Untrusted by default. |
| Other tenants | Untrusted even with full-policy tokens. Assume they can submit arbitrary tool requests and visit hostile pages. The boundary must hold if their browser or tenant worker is compromised, subject to the shared kernel and trusted gateway. |

In 0.27.1 the WebSocket handshake maps a token to a tenant, and sessions belong to a connection. Tenants share the Node service, session manager and service UID. Direct Chromium sessions can share a browser process. The service UID can read every tenant's profiles, cookies, downloads, saved screenshots and recordings under one data root. Child processes can inherit the tenant token environment. The systemd example shares one Xvfb display. [Service assembly](../../src/bosun.mjs), [session manager](../../src/sessions.mjs), [deployment unit](../../deploy/bosun.service).

## 2. Tenant sandbox

### Configuration

| Setting | Accepted values | Default and effect |
| --- | --- | --- |
| `BOSUN_TENANT_SANDBOX` | `off`, `on` | Unset resolves to `off` with zero or one configured tenant token and `on` with two or more. An explicit value always wins over the token-count default. |
| `BOSUN_ALLOW_UNSAFE_MULTI_TENANT` | `0`, `1` | Defaults to `0`. Set to `1` to permit multiple distinct tenants when the sandbox resolves to `off`. It has no effect on mode selection. |

Resolve the mode after validating the existing token configuration. Count the entries parsed from `BROWSER_TOKEN` (one entry mapped to `default` when configured) and `BROWSER_TOKENS` (one entry per configured token), including multiple tokens mapped to the same tenant. Reject invalid switch values. The startup guard counts distinct tenant names in that mapping. If the mode is `off` with two or more distinct tenants, refuse startup before opening listeners unless `BOSUN_ALLOW_UNSAFE_MULTI_TENANT=1`. With the override active in that case, log a warning on every start that tenants share one process and lack OS-level tenant isolation. Keep token values out of the warning.

With the tenant sandbox `off`, use the 0.27 single-process Bosun service on the same host with its existing browser launches, state layout, authentication, token policies and routing. This mode adds no `bwrap`, user-namespace or worker cgroup requirement. The browser's own sandbox keeps its existing 0.27 requirements.

### Sandboxed workers

With the tenant sandbox `on`, run one worker and its browser process trees per tenant with bubblewrap (`bwrap`) on Linux. Agents that need isolation get distinct tenants. A worker can reuse Chromium across sessions of its own tenant. Persistent profiles and meeting browsers retain their separate process lifecycles. Patchright and Camoufox keep their per-session launches. Separate Node processes under the same UID improve crash isolation but share file and network permissions. Separate UIDs add file isolation. Tenant workers share the host kernel. [Bubblewrap security model](https://github.com/containers/bubblewrap#sandboxing).

- **Filesystem and processes.** Use private mount, user, PID, IPC and network namespaces, distinct unprivileged host identities, dropped capabilities and a fresh process session. Mount immutable code, libraries, browser binaries and fonts read-only. Give the worker only its tenant's profiles, uploads, downloads, recordings, screenshots and settings. Use private `/tmp`, `/dev/shm`, `/proc`, and home. Exclude host home, service configuration, control sockets and other tenant roots. Put each headful worker's Xvfb and meeting media helpers in its sandbox. Keep display, audio and clipboard access local to that tenant. Use private driver pipes or inherited sockets. Publish no CDP, Firefox driver, X11 or PulseAudio port.
- **Egress.** A tenant-local loopback proxy connects via a dedicated Unix channel to the tenant's host relay. The relay checks host, port and resolved address and limits selection to the tenant's allowed `BROWSER_EGRESS_PROXIES` exits. `direct` means the relay connects without an upstream proxy. Deny private, loopback, link-local and metadata targets by default, including IPv6. Require equivalent checks at remote-DNS exits for restricted tenants. The private network namespace blocks direct DNS, UDP and WebRTC bypasses. Fail closed on relay or exit failure. [Current proxy](../../src/proxy.mjs), [exit selection](../../src/egress.mjs).
- **Routing.** Keep WebSocket authentication and MCP/MCPL negotiation in the gateway. Resolve the tenant and token policy there, assign a connection lease, and route a typed RPC envelope over a private worker channel. Use the channel's assigned tenant and worker generation plus the lease to check every session operation. Scope downloads, recordings, live-view grants and events to their tenant and appropriate lease. Background keepalive and meeting jobs run under the same tenant worker. Disconnect revokes connection-owned sessions. Worker death invalidates its routes and grants before restart. Local stdio uses a configured single tenant and the same worker boundary.
- **Bootstrap.** Preinstall the pinned Chromium, Patchright and Camoufox packages and binaries. Mount Camoufox's runtime assets and fonts, and keep browser/cache writes tenant-local. Preserve Chromium/Patchright's own renderer sandbox and test Firefox's sandbox and namespace behavior. Preflight each enabled engine under the actual bwrap, AppArmor, systemd or outer-container policy. Nested user namespaces, headful Camoufox/Patchright and media support on target hosts are unverified `?`. Refuse the affected configuration if preflight fails. [Engine launch code](../../src/engines.mjs), [systemd setup](../DEPLOY-SYSTEMD.md#3a-chromiums-sandbox-the-service-will-not-start-without-it).
- **Limits.** Use a cgroup v2 subtree per tenant for CPU, memory, process/thread and I/O limits. Enforce disk quotas and bound sessions, connections, pending requests, transfers and capture buffers. Reap idle workers, kill the worker cgroup on teardown and reserve gateway headroom. **RAM estimate `?`** for one tenant with one ordinary page: 60–150 MiB for the worker, 250–600 MiB for the browser tree and 20–60 MiB for headful display, or about **0.35–0.8 GiB** total. Extra browsers, heavy sites and media can push it above 1 GiB. [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).

**Memory sizing (Misha, 23.11).** VictoriaMetrics sampled the whole Bosun container on `gra` across all three tenants every five minutes over roughly 10.11–23.11. Used memory (`MemTotal − MemAvailable`) was 0.40 GiB on 23.11, with a median of 0.33 GiB, p95 of 0.56 GiB and a sampled maximum of 1.74 GiB against a 6 GiB container limit. Separately, the 0.27.1 Camoufox live-view test matrix peaked at about 1.1 GB for one Camoufox session with live view. Per-tenant workers fit the existing 6 GiB limit, and the **0.35–0.8 GiB** estimate per tenant stays plausible. The per-engine split is not observable today.

The gateway, supervisor, kernel, aggregate limits, read-only binaries and physical disk are shared. A compromised gateway can misroute sessions or disclose ordinary results and artifacts. Keep persistent browser cookies within the tenant boundary and restrict access to signed-in profiles and their backups.

### Metrics

In both modes, export per-session memory distributions, engine memory and active session counts on `/metrics` by tenant and engine (`chromium`, `patchright`, `camoufox`). Use browser process RSS in single-process mode and RSS or cgroup memory in sandboxed mode. For authenticated sessions, use the tenant name mapped from the token as the `tenant` label, including in single-process mode. Use the existing `default` tenant for tokenless local sessions. Count shared browser processes once in engine totals. Keep labels low-cardinality and exclude token values, URLs and session IDs.

In sandboxed mode, also export current, peak and limit memory for each tenant worker's cgroup and a per-worker OOM-kill counter. Worker cgroup series are absent in single-process mode.

Add a Grafana row for session and engine memory and active sessions in both modes, with worker memory, limits and OOM kills when sandboxed. In sandboxed mode, warn when a worker exceeds 80% of its memory limit for 10 minutes. Keep the warning disabled on first deploy and enable it after confirming 10 minutes of valid samples at or below the threshold for each worker.

## 3. 0.28 defaults & configuration

### Configuration contract

Use one schema and loader for environment variables and an optional JSON file selected by `BOSUN_CONFIG_FILE`. Use the same setting names in both. Resolve built-in defaults, then the file's global settings, then environment values. Apply the file's `tenants.<tenant>` overrides for tenant-scoped settings, then explicit per-call arguments where the tool already supports them. Resolve by key. A tenant's list or map replaces the inherited value for that key. Keep listener binds, the data root, provider endpoints and `TZ` global. Resolve tenant behavior the same way in single-process mode and in workers. Existing tenant speech and secret settings keep their 0.27 APIs and persisted values. Feed their persisted overrides through the same resolver as the corresponding tenant file keys so a tool write wins for its key and a reset falls back through the file and global settings. Keep existing environment spellings and formats. Encode lists and maps for new environment keys as JSON. Reject unknown file keys and tenant names other than authenticated tenants and the local `default` tenant.

Use one startup-validated IANA time zone, `TZ`, with default `UTC`, for keepalive wall time and transcript daily usage. Reject invalid names and numeric offsets before opening listeners or starting workers. Browser contexts inherit `TZ` unless `BROWSER_TIMEZONE` is set globally or per tenant, or `session_open.timezone` is passed. Validate configured browser zones and locales at startup. The regular browser locale and the meeting UI locale are independent of the languages spoken or posted during the meeting.

The default guest display name is **Notetaker**. A call's `name` overrides `MEETING_BOT_NAME` for a guest. A signed-in meeting continues to use the account's name where the platform supplies it. The default recording announcement is one English sentence: “This meeting’s audio is being recorded for notes, so please object in chat if you prefer not to be recorded.” The English default for video and live transcription also names the capture that is enabled, including both when selected together.

`MEETING_ANNOUNCE_TEXT` accepts a single string or a map from locale to text. Each locale entry can supply four versions keyed by capture mode (`audio`, `audio_live`, `audio_video`, `audio_video_live`). A single custom string must describe the capture that the deployment enables. `MEETING_ANNOUNCE_LOCALES` optionally selects an ordered list of language tags. With the list omitted, use the single string or the English entry. With a list set, emit one notice per configured locale in that order, using the English built-in only for `en` where custom text is absent. A scalar applies to one locale. Validate tags, duplicates and requested translations at startup. An explicit `meeting_join.announce_text` replaces the generated notices for that join. Both keys support tenant overrides. Chat opt-out matching has its own language selection and continues to watch chat in every announcement mode. The optional `MEETING_OPTOUT_CONFIRM_TEXT` takes `normal` and `live` string entries.

Use reserved example domains for generic host examples. Keep operator hosts, paths and agent names out of code defaults, help and generic README examples. Tool and parameter descriptions should refer to the configured zone without naming a zone or place, including when the operator sets one. Provider URLs belong in descriptions of the supported provider input, and explicitly configured allowlists can still describe their host constraints.

At startup, print the effective global config and tenant overrides once on stderr after validation, including the resolved sandbox mode and the source of each value. Construct this view from an allowlist of safe fields. Show presence and source only for credentials and any unrestricted strings or URLs that could carry secrets, including announce text, proxy URLs and public link bases. Exclude token values, API keys, proxy credentials, signed URLs and the raw environment or file. Apply the same rules to validation errors and worker startup logs. Stdio stdout remains reserved for MCP messages.

## 4. Migration and red-team test plan

**Clients.** Keep the 0.27 client contract, including credential tools, settings and workflows. Reconnect after the service cutover to start new sessions.

**Single-process upgrade.** A 0.27 installation with one tenant token can upgrade in place on the same host with its existing service unit and data directory. Leave `BOSUN_TENANT_SANDBOX` unset to use the default, or pin it to `off`. The single-process path retains the existing state layout and supports browser metrics without the tenant sandbox infrastructure. If an existing multi-tenant installation deliberately keeps the shared 0.27 process, set both `BOSUN_TENANT_SANDBOX=off` and `BOSUN_ALLOW_UNSAFE_MULTI_TENANT=1` and verify the startup warning.

**Sandboxed upgrade (homelab).** With multiple configured tokens, the sandbox is enabled by default. A single-tenant installation can opt in with `BOSUN_TENANT_SANDBOX=on`. Drain 0.27 traffic and stop the service before moving state. Split durable state by tenant with an ownership manifest for named profiles and cookie metadata, keepalive entries, macros, downloads, screenshots, recordings and settings. Verify login continuity and existing retention after moving. Keep the pre-upgrade state for rollback. Update the systemd unit or outer container for bwrap, cgroup delegation, private displays and tenant egress relays. Preflight each deployed engine. Keep TLS and public bind policy explicit. Deploy a test tenant first and apply the metrics alert enablement described above.

**Red-team and release tests.** Use controlled fixture sites and exercise both sandbox modes. Use two distinct tenants for the containment tests.

| Test | Expected result |
| --- | --- |
| Mode selection | With the switch unset, zero and one token select `off` and two or more tokens select `on`. Exercise both token settings, including two tokens mapped to one tenant. ## Later: credentials (not scheduled)

These design notes require an owner walkthrough before scheduling. The proposed resolver, recipe API, fill and export flows, provider integrations and client migration are outside the 0.28 release and its test plan.

### Threat model and 0.27 baseline

The operator approves credential policies. A separate trusted client-side resolver supplies a value for one approved browser operation, using only approved sources and sinks. Bosun keeps neither a credential inventory nor a retrievable copy of the value. A model-controlled shell gets neither resolver credentials nor arbitrary resolver access. The model is untrusted with plaintext, vault tokens and authorization decisions. Approving a credential destination trusts that page and its scripts with the value. They can read, retain or forward it. The same applies to a site that displays a newly generated key. Keep provider tokens and protected payloads out of the gateway and launch environment.

`secret_create` holds the PUT value in memory for up to 10 minutes. `secret_save` stages plaintext on disk for up to 15 minutes. `secret_reveal` and unmasked `read` can send values to client transcripts. Screenshots and ordinary reads rely on heuristics. Live view sends browser pixels under a bearer link, and meeting video records raw Chromium CDP frames. CDP access can expose DOM values, cookies and network data. Chromium and Patchright use CDP internally, with no general CDP tool in MCP. Page echoes can reach URLs, titles and artifacts. Driver logs, Node diagnostics and intermediary logs can expose payloads or bearer links. [Secrets](../../README.md#typing-secrets), [tools](../../src/tools.mjs), [live view](../../src/liveview.mjs), [meeting video](../../src/meetings/video.mjs).

### Credential operations

An operator registers a recipe per tenant with the source or allowed sink aliases, HTTPS entry URL, exact top and frame origins (scheme, host, port), and unique CSS target and field type. A fill recipe sets the submit action, HTTPS form destination and success check. An export recipe sets the generation action and property (`value` or `textContent`) to read. The resolver maps aliases to a provider and reference and authorizes the recipe, account and destination independently of MCP. The model can request a recipe by name. All selectors, paths and destinations come from policy.

#### API

| Surface | Request and result |
| --- | --- |
| MCP `credential_fill_prepare` | `{session, recipe_id}` → `{operation_id, status: "pending", expires_in_s: 30}`. Full-policy only and scoped to the connection's session. |
| MCP `credential_export_prepare` | `{session, recipe_id, sink_id}` → same result and access rules. Both policies must approve `sink_id`. |
| MCP `credential_status` | `{session, operation_id}` → `{status}`. States are `pending`, `running`, `submitted`, `committed` and `error`. Errors include `code`. |
| Resolver `POST /v1/credential-ops/{id}/claim` | Over an authenticated tenant-scoped channel. Verify resolver approval of the bound session, recipe version, origins and destination. Issue a single operation token to the resolver. The MCP operation ID alone conveys no authority. |
| Resolver `PUT /v1/credential-ops/{id}/fill` | Operation token in `Authorization: Bearer`, plus the authenticated resolver channel. Body is 1–4096 bytes of UTF-8, exact bytes with no newline trimming. Respond only with status and a fixed error code. |
| Resolver `POST /v1/credential-ops/{id}/export` | Same authentication and single-use token. Empty request, one streamed UTF-8 response of up to 4096 bytes to the resolver. Resolver sends `POST /v1/credential-ops/{id}/receipt` with `{status: "committed"}` after sink commit, using its authenticated identity. |

Use mutual TLS to the credential worker through a gateway relay, or a permissioned Unix socket locally. Route on configured tenant endpoints and verify resolver identity at the worker. Bind the token to that identity, tenant, session lease, worker generation, recipe version and operation kind. Allow one pending operation per session. Start the 30-second claim/use window after the gate is ready. Atomically spend the token before reading the body or generating a key, then allow up to 15 seconds to execute. Resolver approval and provider login can happen beforehand. Disconnect, revocation and restart invalidate grants. Keep only short-lived status records.

Use `INVALID_ARGUMENT` (400), `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404 for unknown, foreign, expired or spent grants), `BUSY` (409), `TOO_LARGE` (413), `DEADLINE` (408), `ORIGIN_MISMATCH` or `TARGET_CHANGED` (422), and `UNAVAILABLE` (503 for an unsafe or unavailable worker). Use terminal status `SINK_FAILED` for a confirmed unsuccessful write and `OUTCOME_UNKNOWN` if execution or commit may have happened. MCP reports codes without HTTP status, plus `PROTECTED_SESSION` for ordinary requests during the operation. Return fixed messages without page text, URL, title, value hash, length or driver exception.

#### Fill and resume

1. Lock the session before the credential job opens its approved page. Refuse new page actions and reads, macro steps, handoff, screenshots and capture subscriptions. Revoke live-view grants, drain pending reads and inputs, stop recorders and detach capture drivers. Drop queued frames, diagnostics and content events from the previous session generation. Abort if the gate cannot be confirmed. Meeting capture and credential operations cannot run in the same session.
2. The trusted supervisor starts a fresh protected browser in the tenant sandbox with a private tmpfs profile, clipboard and driver pipe. Give the job a separate PID/mount boundary and process identity from ordinary tenant processes. Open the configured page with egress limited to recipe hosts and ports. Before reading plaintext and again at use, check top/frame origins, document generation, the unique attached element, field type and submit destination. Pin the element to its document and use element-scoped input without retargeting or global keystrokes. Abort on document, focus or target change, opaque origins or unapproved redirects. Allow cross-origin submits only to exact destinations in the recipe. Race-free binding under navigation and focus changes needs verification on each engine `?`.
3. Fill, submit and check the configured success condition while sealed. Clear the field if it still exists, overwrite owned buffers in every exit path, then terminate the protected browser and short-lived fill process and discard the tmpfs. Disable traces, dumps, request/body and protocol logging, password saving and persistent storage for protected jobs. Prevent swap for those processes. Driver and browser memory can contain copies until teardown. Return `submitted` only after the success check and teardown. On timeout, crash, isolation failure or ambiguous cleanup, fail closed and retire the affected session.
4. Resume ordinary actions in a clean browser after teardown. For a vetted site, a recipe can carry explicitly named, host-only `Secure`/`HttpOnly` session cookies into a fresh context for that host `?`. The reverse transfer can seed an export from an approved signed-in profile. Transfer only those cookies and only for sites that keep the input or generated value out of future responses. Recipes without cookie transfer return status and close the protected browser.

#### Three resolver flows

- **File, environment or SOPS.** A trusted local helper maps the approved alias to a private file or environment variable, or decrypts and extracts a SOPS field. It pipes the selected bytes directly to the one-shot PUT as in 0.27, with a deadline in seconds and immediate use. The helper controls newline handling. Keep payloads out of command arguments, shell tracing, terminal output and model-visible tools. This works without a vault.
- **OpenBao.** The authorized source requests a read with a short response-wrap TTL, for example 20 seconds once the operation is ready. Hand the single-use wrapping token privately to the resolver. It checks the creation path against policy, unwraps once at the pinned OpenBao endpoint, extracts the approved field and sends the fill PUT. Abort on unexpected path, expiry or prior use. The wrapping token authorizes the OpenBao unwrap and the Bosun token authorizes the browser operation. OpenBao is optional and Bosun holds no OpenBao identity or token. [OpenBao response wrapping](https://openbao.org/docs/concepts/response-wrapping/).
- **1Password or Bitwarden.** Map the alias to an `op://` field resolved with `op read` or to a Bitwarden Secrets Manager item ID resolved with `bws secret get` and local field extraction. The resolver holds the provider identity with access limited to the approved data. Capture the provider result privately and send only the selected field. The same contract can accommodate an approval-based provider. [1Password CLI](https://www.1password.dev/cli/reference/commands/read), [Bitwarden CLI](https://bitwarden.com/help/secrets-manager-cli/).

#### Write a newly generated key to a sink

Arm the gate **before** clicking Generate. Check origin and document at generation and again at read. Stream the approved element's value over the active resolver request and tear down the protected browser, retaining no file or later fetch path. The resolver commits to its configured vault entry or atomically writes a `0600` file in its private directory. Report `committed` after teardown and receipt. The resolver records commits by `operation_id` so a lost receipt can be reconciled without regenerating the key. On uncertainty, check the sink first and revoke any orphaned key before retrying. Rotate a key already exposed in a transcript or recording.

### Proposed migration

**Clients.** Announce deprecation before removing `secret_create`, `/secret/*`, `type.secret_id`, its `allow_non_password` option, `secret_save`, `secret_reveal`, `secret_settings_get/set`, `secrets_reveal` and `SECRETS_REVEAL`. Remove the saved-secret variant of `download_get`. Keep ordinary downloads and default read/screenshot masking. Reject legacy arguments explicitly where the SDK might otherwise drop them. Move secret-bearing `macro_run` workflows to client orchestration that calls the resolver between ordinary steps. Flag stored versions that use the old parameters with a migration error. Keep operator-controlled human handoff for unsupported login flows.

**Homelab.** At credential cutover, drain traffic and stop the service to invalidate in-memory secrets, links and old sessions. Purge legacy secret staging before taking a new backup. Remove reveal settings and look for earlier values in logs, artifacts, backups and client transcripts. Rotate where exposed. Move file/SOPS/provider configuration to the resolver. Keep the old secret endpoints inaccessible during a rollback from the credential cutover.
