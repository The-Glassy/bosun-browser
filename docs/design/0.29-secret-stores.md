# Bosun 0.29 — secret stores

Updates the "Later: credentials (not scheduled)" part of the 0.28 design
(`docs/design/0.28-isolation-and-secrets.md`, PR #48) for what has happened since: 0.28 shipped per-tenant bubblewrap
workers, the `secret_*` tools stay, and defaults may not change silently. Sections 1–4 of that document (sandbox,
metrics, defaults, migration) are 0.28 history and are not repeated here. `RESEARCH-secrets.md` holds the survey of
Browserbase, Browser Use, 1Password, Bitwarden, Anthropic, OpenAI and the OpenBao API that this design was checked
against.

Everything below is **off unless `BOSUN_SECRET_STORES` is set**. Without it 0.29 has no new tool, no new argument, no
audit log and no new process or socket.

## 1. What changed against the 0.28 document

### Kept

- **The goal.** A credential reaches a page without passing through the model, and a key generated on a page goes
  straight to a store or a `0600` file.
- **Recipes are the operator's.** Per tenant; the model can only name one. Store, path, origin, field selector, field
  type and submit destinations all come from policy, never from a tool argument or from page content.
- **Exact origins.** Scheme, host and port, HTTPS only (HTTP on loopback for development and tests). No wildcard and
  no subdomain matching.
- **The three sources**: file / environment, OpenBao (with a single-use wrapping token), 1Password and Bitwarden.
- **Fixed error codes without page text or values**, and results that are a status.
- **An agent-side resolver stays possible**: a recipe with `store: "client"` binds a value sent through the existing
  one-time PUT (`secret_create`) to the same page checks.
- **Trust statement.** Approving a destination trusts that page and its scripts with the value.

### Changed

| 0.28 document | 0.29 | Why |
| --- | --- | --- |
| Bosun has no store access; only a client-side resolver does | Bosun's **gateway** (or the single process) can read the stores the operator configures. Workers, browsers and the model cannot. The client-side resolver remains as `store: "client"` | 0.28 gave us a trusted component that is outside every tenant's sandbox and off the model's path: the gateway. Using it removes a second deployment (resolver, mTLS, claim protocol) for the common case, and the store token still never enters a sandbox |
| `credential_fill_prepare` / `credential_export_prepare` / `credential_status` + resolver HTTP API (claim, fill, export, receipt) | Two tools: `secret_recipes`, `secret_fill`; plus `secret_save` with `store_target` | One synchronous call is enough when the resolver is in-process. No operation ids, tokens or status polling to get wrong |
| A fresh protected browser on tmpfs per fill, session locked, cookies carried over | The fill happens in the agent's own session, serialised with its other calls, and the value is then **guarded**: scrubbed from every later result of that session (section 5) | The protected browser cannot log a real profile in (the login must land in the profile the agent uses), and cookie hand-over was marked `?` in 0.28. Guarding outputs gives the property we need — the value does not reach the model — at a fraction of the machinery. Residual: the page's own scripts see the value (as before), and the browser process holds it until the session closes |
| Export recipes with a generation action | `secret_save … store_target, store_key`: the agent does the clicking, Bosun moves the element's value to the store | The agent already drives the page; only the value must bypass it |
| `secret_*` tools deprecated and removed | **Kept, unchanged by default, and hardened** (section 7). The store path is additive | Misha: needed when an agent generated a PAT and must reuse it |
| Submit action, form destination and success check in the recipe | `submit` (press Enter) and `submit_to` (allowed form destinations, checked before the fill). No success check | A declared success URL is useful but not required for the secrecy property; deferred |
| mTLS / permissioned Unix socket between resolver and credential worker | A Unix socket per worker, in that worker's read-only relay directory; the socket *is* the tenant | Same mechanism 0.28 uses for egress relays |

### Dropped

- The claim/token protocol, operation states and `OUTCOME_UNKNOWN` / receipt reconciliation.
- Revoking live view, stopping recorders and detaching capture drivers around a fill: page tools and a handoff
  already exclude each other, meetings run in sessions the agent cannot address, and the guard covers what remains.
- Removing `secret_create`, `type.secret_id`, `allow_non_password`, `secret_save`, `secret_reveal`,
  `secret_settings_*`, `SECRETS_REVEAL` and the saved-secret variant of `download_get`; the "legacy cutover" tests.
- SOPS as its own adapter: `sops -d … | curl -T - <put_url>` with a `client` recipe (or a decrypted file in a file
  store) covers it.

## 2. Threat model

| Actor | 0.29 position |
| --- | --- |
| Operator | Writes `BOSUN_SECRET_STORES`, owns store tokens and the audit log. Trusted. |
| Gateway / single process | Trusted with store tokens and, transiently, values. |
| Tenant worker (sandbox on) | Gets one value at a time for a recipe of **its** tenant, in memory. Holds no store address, token or path. A compromised worker can obtain exactly what its tenant's recipes name — and nothing of another tenant. |
| Model / agent | Untrusted with plaintext and with authorisation. Sees recipe names and bindings, statuses and fixed error codes. |
| Page at the recipe's origin | Trusted with the value by the operator's decision. Can read, keep or forward it. |
| Other pages, other tenants | Never receive a value: origin, field and form destination are checked before the store is asked. |
| A human with a handoff link | Not trusted with store values: they are removed from the page before the live view starts. |

Out of scope, as in 0.28: host root, a compromised gateway, what a logged-in session can do afterwards (the session
cookie is the real credential once the login succeeded), and exfiltration by the approved page itself.

## 3. Configuration (installation and tenant level)

One setting: `BOSUN_SECRET_STORES` — a JSON object, or the absolute path of a JSON file. Validated at start; an
unknown key, store, tenant or a non-HTTPS origin stops the service. Nothing in it is a secret value.

```json
{
  "stores": {
    "bao":   { "type": "openbao", "address": "https://bao.example.org:8200", "mount": "secret",
               "token_file": "/run/credentials/bosun/bao-token" },
    "files": { "type": "file", "dir": "/var/lib/bosun-secrets" },
    "env":   { "type": "env", "prefix": "BOSUN_SECRET_" }
  },
  "recipes": {
    "sso-password": { "store": "bao", "path": "tenants/{tenant}/sso", "field": "password",
                      "origin": "https://login.example.org", "selector": "input#password", "submit": true,
                      "submit_to": ["https://login.example.org/session"] }
  },
  "save_targets": {
    "generated": { "store": "bao", "path_prefix": "tenants/{tenant}/generated/", "origins": ["https://github.com"] }
  },
  "tenants": {
    "alice": {
      "recipes": { "github-otp": { "store": "client", "origin": "https://github.com", "selector": "#app_totp", "field_type": "text" },
                   "sso-password": null },
      "save_targets": { "generated": { "store": "files", "path_prefix": "alice/", "origins": ["*"], "overwrite": true } }
    }
  }
}
```

- **Installation level**: `stores`, and `recipes` / `save_targets` that apply to every tenant with policy `full`.
  `{tenant}` in a path is replaced per tenant, so one entry cannot make tenants share a path by accident.
- **Tenant level**: `tenants.<name>.recipes` / `.save_targets`. An entry of the same name replaces the installation
  one; `null` removes it for that tenant.
- A tenant with policy `ephemeral` never gets recipes or targets; naming one is a startup error.
- Tenants cannot define or change recipes through a tool. That is deliberate: the model must not authorise itself. The
  existing tenant-level `secret_settings_*` (`secrets_reveal`) is unchanged.

Recipe: `store`, `path`, `field?`, `origin`, `path_prefix?`, `selector`, `field_type?` (default `password`; `text`,
`email`, `tel`, `number`, `url`, `search`, `textarea`, `any`), `submit?` (default false), `submit_to?` (default: the
origin), `description?`. Save target: `store`, `path_prefix`, `field?`, `origins` (required; `["*"]` must be written
out), `overwrite?` (default false), `description?`.

## 4. Store adapters

`src/stores/adapters.mjs`. One interface: `read(path, field) → Buffer`, `write(path, field, value, {overwrite})`,
`close()`. Paths are 1–10 segments of `[A-Za-z0-9._-]`, each starting with a letter or digit (no `..`, no absolute
path, no empty segment). Values are 1–4096 bytes of UTF-8. Every failure is a `StoreError` with one of `NOT_FOUND`,
`FORBIDDEN`, `EXISTS`, `INVALID`, `TOO_LARGE`, `UNSUPPORTED`, `UNAVAILABLE`; messages never carry a value, a token or
a response body.

| Type | Read | Write | Notes |
| --- | --- | --- | --- |
| `file` | file under `dir`; with `field`, a string member of a JSON file | `0600` file in `0700` directories, atomic; create-only unless `overwrite` (hard link, so two writers cannot both win) | Links out of `dir` are refused. `read_only: true` available |
| `env` | `PREFIX` + path in capitals | – | Values are taken at start and removed from the process environment |
| `openbao` (`vault`) | KV v2 `GET /v1/<mount>/data/<path>` → `data.data[field]` (default field `value`); KV v1 with `kv_version: 1` | read–merge–`POST` with `options.cas` (0 for a new entry, the read version otherwise), so other fields are kept and a concurrent writer is noticed | `token_file`, or `wrapping_token_file` (+ `wrapping_creation_path`): a single-use wrapping token is looked up, its creation path compared for equality, then unwrapped once on first use. `namespace`, `ca_file`, `timeout_ms`. HTTPS only (HTTP on loopback). Redirects are an error |
| `1password` | `op read --no-newline op://<path>/<field>` | – | Experimental: tested against a stand-in CLI, not the real service. Token from `token_file` in `OP_SERVICE_ACCOUNT_TOKEN`, never on the command line; minimal environment |
| `bitwarden` | `bws secret get <id> --output json` → `.value` | – | Experimental, as above (`BWS_ACCESS_TOKEN`) |

1Password's Agentic Autofill and Bitwarden's Agent Access (human approval, Noise channel into an extension) are a
different integration shape; the adapter interface does not preclude them but they are not attempted.

## 5. Fill by recipe

`secret_fill { session, recipe, secret_id?, timeoutMs? }` → `{ recipe, status: "filled" | "submitted", url, title }`.

Order of checks; the store is asked only after all of them pass:

1. The recipe exists for this tenant (same answer for "unknown" and "another tenant's").
2. Driver debug logs that print typed values are off (as for `type secret_id`).
3. The top-level page's origin equals the recipe's, and its path starts with `path_prefix`.
4. `selector` matches **exactly one** element in the top-level document (not zero, not two, not inside a frame).
5. The element is an `<input>`/`<textarea>` of the recipe's `field_type`, enabled and writable.
6. If the field has a form: its `action` attribute (not the property, which an `<input name=action>` replaces), and
   every `formaction` of its buttons (inside the form or attached by `form=`), resolve to a `submit_to` destination.
7. The field is marked sensitive; then the value is read (store, or the `secret_id` slot for a `client` recipe).
8. Page and element are checked again (the store call took time), the value is typed into that element handle, and
   the landing check of `type secret_id` applies: if the value is not in that element, the page is scrubbed and left.
9. `submit: true` presses Enter in the field.

Error codes in the audit log: `ORIGIN_MISMATCH`, `TARGET_NOT_FOUND`, `TARGET_NOT_UNIQUE`, `TARGET_NOT_EDITABLE`,
`FIELD_TYPE`, `SUBMIT_TARGET`, `TARGET_CHANGED`, `INVALID`, the store codes, `FILL_FAILED`. The message to the agent
names the observed origin or element type (as Browser Use's `domain_not_allowed` does), never page text.

### Masking guarantees

From the moment a value leaves the store until its session closes, the worker keeps it in memory (`SecretGuard`) and:

- **Every text a tool returns or throws** to that tenant is scrubbed of it — literal, URL-encoded (both forms),
  JSON-escaped, base64, base64url and hex. This covers `read` (also with `secrets_reveal` on), URL and title in every
  result, `sessions`, macro results and error messages, whatever the page did with the value (echoed it, put it in
  its URL, mirrored it into another element).
- **`secret_reveal` and `secret_save` to a download refuse** an element whose value contains it.
- **Screenshots** cover every element showing it, in addition to the field (marked sensitive, as today).
- **Human handoff**: before the live view starts, the value is removed from every field and text node of the page; if
  that cannot be done the handoff is refused. A viewer could otherwise toggle a password field to plain text.
- **Recording**: meeting audio/video capture only meeting sessions, which no connection can address, so a fill cannot
  happen in a recorded page. Saved screenshots (`SAVE_SHOTS=1`) are the masked ones.
- **Logs and audit**: the id of the recipe, never the value or its length.

Not guaranteed (documented in README): a value shorter than 3 characters is not scrubbed; a page that transforms the
value (hashes it, splits it across elements, draws it on a canvas) can show the transformed form; the approved page's
scripts can send it anywhere.

## 6. Write-back of generated secrets

`secret_save { session, <target>, store_target, store_key, overwrite? }` reads the element exactly as `secret_save`
does today, then writes to `<path_prefix><store_key>` in the target's store instead of staging a download. The page's
origin must be in the target's `origins`; `store_key` is `[A-Za-z0-9._-]{1,64}`; an existing entry is an error unless
the target allows `overwrite` and the call asks for it. Result: `{ stored, store_target, key, version?, length,
sha256_prefix }` (no prefix under 16 bytes). The saved value joins the guard: it is masked in that session from then
on. To use it in a browser later, the operator adds a recipe that reads the same path; the agent's own shell reads it
from the store with its own credentials.

## 7. The existing secret tools

`secret_create`, `type secret_id` / `allow_non_password`, `secret_save`, `secret_reveal`, `secret_settings_get/set`,
`SECRETS_REVEAL`, `download_get` for saved secrets: all kept. Hardening in 0.29 (review findings 6 and 7):

- A typed secret that the page put into its URL or title is scrubbed from later results of that session (it used to
  be masked only in the `type` result).
- `secret_save` returns no `sha256_prefix` for values under 16 bytes.

Migration path, for those who want one: (1) keep using `secret_create` + `type secret_id` — nothing to do; (2) add a
`client` recipe to pin where such a value may go (`secret_fill { recipe, secret_id }`); (3) move the value into a
store and switch the recipe's `store` — the agent's call loses its `secret_id`, nothing else changes; (4) replace
`secret_save` + download with `secret_save … store_target`. No step is forced and no deprecation is announced.

## 8. Tenant sandbox

- `SecretStores` lives in the gateway. `workerConfig` sets `secretStores: null`; the serialised worker configuration
  contains no store address, token path or store path (tested).
- For a tenant with at least one recipe or target, the gateway listens on `<relay>/secrets` (mode `0600`, in the
  worker's own read-only relay directory, next to its egress sockets) and serves `GET /list`, `POST /resolve`,
  `POST /save`, `POST /note`. The tenant is fixed by the socket; a request cannot name another one.
- The worker has no network namespace route to the store and no token. It checks the page (it drives the browser), asks
  for one value, types it, and keeps it only in the guard until the session closes.
- The audit log is in the data root, outside every `tenants/<name>/` directory: no worker can read or rewrite it. A
  worker's own audit notes (fill outcome) are stamped with the socket's tenant and limited to a fixed set of fields.
- Shared mode (`BOSUN_TENANT_SANDBOX=off`): the same interface in-process.

## 9. Audit log

`<BROWSER_DATA>/audit/secrets.jsonl`, `0600` in a `0700` directory, one JSON line per operation, also on stderr
(`bosun: secret-audit {…}`); rotated to `.1` at 10 MB. Fields: `ts, tenant, action (resolve | fill | save), recipe |
target, key, store, path, field, session, origin, status (ok | refused | error), code`. Never a value, a length or a
hash.

## 11. Deferred

- A declared success condition (`success_url`) and clearing the field after submit.
- Fields inside frames (a frame-origin binding), TOTP seeds as a secret type, recipes as macro steps.
- A protected throw-away browser for fills on sites that echo credentials.
- 1Password Agentic Autofill / Bitwarden Agent Access; real-service tests for the CLI adapters.
- Per-recipe rate limits and human approval per fill.
- Reloading `BOSUN_SECRET_STORES` without a restart.
